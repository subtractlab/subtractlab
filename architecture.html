MeaningSpace architecture / technical disclosure

One human, one AI,
and five stand-ins.

MeaningSpace is a semantic memory OS for an AI — and at the same time a commander architecture that turns web Claude itself (the chat page in a browser) into a group of sub-agents running in parallel at ¥0 extra API cost. This page lays out the whole structure, illustrated: DP multi-agent, self-learning, self-repair, and the execution layer (checks).

Digital anchor — first published 2026-07-16 (JST). The date each mechanism went live is given in the text and in the prior-art timeline. The git commit history of this repository serves as a tamper-evident timestamp.

Overview — three layers and a commander

There are only four parts. (1) A human talks; (2) the commander AI (Eliza = Claude Desktop) decides; (3) the semantic memory (MeaningSpace / DuckDB) supplies the past; (4) the DP lanes (stand-ins of web Claude) do the work in parallel.

In plain words: the owner (human) only talks to a capable secretary (the commander AI). The secretary pulls the company records (semantic memory), hands work to five part-timers (DP lanes), checks what comes back, and reports — all inside one PC.

DP multi-agent — orchestrating web Claude (foundation fixed 2026-07-13)

DP = Debug Port. Chrome's debugging interface (CDP, the Chrome DevTools Protocol) drives the claude.ai chat page mechanically. One lane = one Chrome = one profile = one CDP port. With zero shared state, adding lanes does not break the structure.

In plain words: there are usually two ways to give an AI work — chat with it yourself, or use the developer API (pay per use). DP is a third way: five robot hands that operate the chat page, working five screens at once inside a flat-rate plan. That is why the extra cost is ¥0.

Active coding — the one who touches and the one who decides

Claude in a browser has no file system, so the roles are split. Python (the commander's execution layer) touches; the DP agent decides. (1) Python reads files and injects them into the prompt (hydration) → (2) DP returns only a diff or a new body → (3) Python applies, runs and verifies it. Because the commander itself has checks and checks , a loop forms in the middle of a conversation: write code, run it, look at the result, and send a fix back to DP.

In plain words: the architect (DP agent) only draws plans; the carpenter on site (the Python execution layer) builds and load-tests. If the test fails, the plan goes back. The architect never gets a hammer (delete permission) — that is the core of the safety.

AutoCrystallize V2 — a pipeline that turns conversations into memory

A fully automatic pipeline that turns conversation logs into crystals (structured units of memory). Manual copy-and-paste was removed (2026-06-13), and all eight steps were proven on the DP route (2026-07-13).

Self-learning — the SelfEval loop (implemented 2026-07-08)

Each time a conversation is crystallized, a SelfEval crystal grades how the AI itself worked. Strengths and weaknesses accumulate with decay (EWMA, an exponential moving average) and are worn automatically at every boot as behavioral norms, self_preferences. In short, yesterday's failure is built into today's starting state.

Self-repair — SelfRepair (designed 2026-07-08)

If self-learning corrects behavior, self-repair fixes structure. When a weakness score drops past the threshold (≤ −3.0), the system files a Task crystal (a repair ticket) on its own. One word from the human — "let's do maintenance" — and the commander bundles the tasks and clears them with a DP swarm.

In plain words: the daily work report (SelfEval) updates the performance review (self_preferences), which is handed back at the next morning's briefing. If a bad habit gets serious, a ticket to fix the underlying mechanism is cut automatically — reflection turned into a mechanism instead of a feeling.

The allowance is shared across the account (a rolling 5-hour window plus a weekly limit). DP is not a loophole in billing; it is a way of designing parallelism within a flat-rate allowance.

Relation to similar systems

Agentic coding tools (for example, Claude Code) are designed around a single agent working from a terminal. What is specific here is threefold: (1) a ¥0 route that turns the chat UI itself into parallel sub-agents; (2) a persistent semantic memory and a self-improvement loop permanently wired to the commander; and (3) active coding, in which the commander fires checks mid-conversation and sends work back to DP on the strength of the results.
